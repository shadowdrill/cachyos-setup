# RDP Handoff: KRDP on a New CachyOS Install

How to get Windows Remote Desktop (mstsc) into a **live CachyOS Plasma Wayland session** using KDE's KRDP server. This covers everything learned while fixing it on `cachyos-taichi` (15–16 October 2026), written so it can be repeated on a fresh install.

Related files in this repo:

- `docs/rdp/SETUP.md`: record of the working setup on cachyos-taichi
- `docs/rdp/HANDOFF.md`: original problem report and history
- `docs/rdp/KRDP-Remote-Desktop-Guide.docx`: end-user guide (generated by `scripts/rdp/make_guide.py`)
- `scripts/rdp/krdp-build/`: PKGBUILDs and patches used

---

## 1. Quick start (fresh install)

Run these steps in order. Steps 3 and 4 depend on the krdp version CachyOS ships at the time (see section 2).

### 1.1 Install and enable KRDP

```bash
sudo pacman -S --needed krdp
kcmshell6 kcm_krdpserver
```

In the Remote Desktop settings page:

- Enable the RDP server.
- Under **System Users**, enable your login user. This is PAM auth with your normal Linux password.
- Don't add anything under **Other Users**. An "Other Users" entry with an empty password breaks the login check (section 5.6).

Check it's running:

```bash
systemctl --user status app-org.kde.krdpserver.service
ss -ltn | grep 3389
```

### 1.2 Check versions

```bash
pacman -Q krdp freerdp plasma-desktop
```

Use the table in section 2 to decide whether you need a local build.

### 1.3 Replace the 1-day certificate (always do this)

The settings page generates a self-signed certificate valid for **1 day** with no hostname. Replace it with a long-lived one and stop it being regenerated:

```bash
mkdir -p ~/.local/share/krdpserver && cd ~/.local/share/krdpserver
IP=$(ip -4 route get 1.1.1.1 | awk '{for(i=1;i<=NF;i++) if($i=="src") print $(i+1)}')
openssl req -x509 -newkey rsa:2048 -nodes -days 3650 \
  -keyout krdp.key -out krdp.crt -subj "/CN=$(hostname)" \
  -addext "subjectAltName=DNS:$(hostname),IP:${IP}" \
  -addext "extendedKeyUsage=serverAuth"
chmod 600 krdp.key
kwriteconfig6 --file krdpserverrc --group General --key Certificate "$HOME/.local/share/krdpserver/krdp.crt"
kwriteconfig6 --file krdpserverrc --group General --key CertificateKey "$HOME/.local/share/krdpserver/krdp.key"
kwriteconfig6 --file krdpserverrc --group General --key AutogenerateCertificates false
systemctl --user restart app-org.kde.krdpserver.service
openssl x509 -in krdp.crt -noout -subject -enddate   # expect ~10 years
```

### 1.4 Connect from Windows

1. Run `mstsc` and click **Show Options**.
2. Computer: the Linux machine's IP address.
3. User name: your Linux username, exactly (e.g. `hs`). With krdp < 6.8.1, don't use `.\hs` or `PC\hs`.
4. Tick **Allow me to save credentials**. If old saved credentials exist, click **Delete** first.
5. Connect and type the **Linux** password (not the Windows/Microsoft one).
6. At the certificate warning, tick **Don't ask me again for connections to this computer** and click **Yes**.

KRDP has no login screen of its own. Windows must send the password up front, which is why saved credentials matter.

The Linux side must be logged in to Plasma; KRDP shares the existing session.

### 1.5 Connect from a Mac

Use **Microsoft Remote Desktop** (free, from the Mac App Store) or **Jump Desktop** as a fallback. KRDP itself is protocol-compatible with mstsc, but Mac clients cache the password in a way that causes every retry to fail unless you clear the cache first (see §3.6).

Quick recipe with Microsoft Remote Desktop:

1. **Add a PC**: Connection name anything; **PC name** = the CachyOS box's IP (e.g. `192.168.0.101`).
2. **User Account** = "Ask me every time". Don't pick "Add user account" — it stores the password in Keychain and you'll re-send the wrong one on the next attempt.
3. **Display** tab: pick a single resolution (the default works). Avoid "Multiple displays" — KRDP only exposes one virtual monitor.
4. **Sound**, **Folders**, **Clipboard**: turn **off** unless you need them. Clipboard sharing has caused stalls in older KRDP builds.
5. **Gateway** tab: leave blank.
6. Save and double-click the connection. At the password prompt, type the **Linux** password (not your Mac user password). Make sure your Mac keyboard layout matches what you used when you set the CachyOS password; UK vs US swaps `@`, `"`, `#`, `\`.
7. At the certificate warning (10-year self-signed, see §1.3), accept it. Once accepted, MRD won't ask again.

If login fails with "An authentication error has occurred" or just keeps rejecting the password:

- See **§3.6 Mac client** for the full diagnosis and the "clear Keychain + reset faillock" recipe.
- The CachyOS account gets locked by `pam_faillock` after 3 failed attempts in 15 minutes. From the Mac, run `ssh hs@<cachyos-host> 'sudo faillock --user hs --reset'`. If SSH is also locked, wait ~10 minutes for the lock to expire.

The Linux side must be logged in to Plasma; KRDP shares the existing session.

## 2. Which krdp version needs what

| krdp version (with freerdp ≥ 3.32) | Login | Picture (Windows client) | Action |
|---|---|---|---|
| ≤ 6.7.5 (repo build) | **Fails**: `Could not find user in SAM database` | n/a | Build 6.7.5 with patches (section 4.2), or upgrade Plasma |
| 6.7.5-3 (local patched) | OK | OK | Nothing |
| 6.8.0 (repo build) | OK, but user must type exactly `hs` | **Black screen** (stream freezes after ~6 frames) | Build 6.8.1 (section 4.1) |
| **≥ 6.8.1** | OK | OK | Nothing: use the repo package |

To check whether the repo already has a good version:

```bash
pacman -Si krdp | grep Version
```

If it's 6.8.1 or newer, install from the repo and skip section 4 entirely.

Don't put krdp in `IgnorePkg`. The local builds use version numbers chosen so the repo package replaces them automatically once it's newer (section 4.4).

## 3. Problems found, root causes and evidence

### 3.1 FreeRDP 3.32 ExtSecurity default (login always fails)

**Symptom** (`journalctl --user -u app-org.kde.krdpserver.service`):

```
[ERROR][com.winpr.sspi.NTLM] - [ntlm_fetch_ntlm_v2_hash]: Error: Could not find user in SAM database
[ERROR][com.freerdp.core.auth] - [credssp_auth_authenticate]: AcceptSecurityContext status SEC_E_NO_CREDENTIALS [0x8009030e]
[ERROR][com.freerdp.core.transport] - [transport_accept_nla]: client authentication failure
```

It is reproducible locally without Windows:

```bash
krdpserver --plasma --address 127.0.0.1 --port 3390 --username testprobe --password 'tmp-pass'
xfreerdp3 /v:127.0.0.1:3390 /u:testprobe /p:'tmp-pass' /cert:ignore /auth-only
```

**Root cause:** FreeRDP commit `a1fad13` ("[core,security] add ExtSecurity to all clients and server", September 2026) changed `FreeRDP_ExtSecurity` (PROTOCOL_HYBRID_EX) to default TRUE. KRDP 6.7.5 is designed for TLS + PAM. It sets `NlaSecurity=false` but didn't know about `ExtSecurity`, so clients negotiated HYBRID_EX (CredSSP/NTLM). FreeRDP then looked for an NTLM SAM database that KRDP never creates.

**How it was found:**

- `nm -D /usr/lib/libKRdp.so.*` showed no `freerdp_settings_set_string` (so no SAM file path is set), and the KRDP 6.7.5 source sets only Rdp/Tls/Nla security.
- `objdump -d` confirmed KRDP passes the correct setting IDs (0x441 = NlaSecurity), so it wasn't an ABI mismatch.
- `git log 3.31.0..3.32.2 -- libfreerdp/core/{nego,peer,settings}.c` in FreeRDP found the default change.

**Fix:** KRDP commit `573e40a` (Plasma/6.7) / `4eb3dff` (master), "Fix authentication with FreeRDP 3.32", KDE bug **526514**. It adds `freerdp_settings_set_bool(settings, FreeRDP_ExtSecurity, false);`. Included from krdp 6.8.0.

### 3.2 mstsc sends `DOMAIN\user` (login silently rejected)

**Symptom:** `New client connected: Windows platform Windows NT`, then `PostConnect … failed` with **no `pam_unix` line at all**.

**Root cause:** `RdpConnection::onPostConnect()` only runs PAM if `username == KUser().loginName()`. mstsc often sends `PCNAME\hs` or `.\hs`.

**Fix:** KRDP master commit `095f6ea` / Plasma/6.8 commit `d6b12bf` strips everything before the last `\`. Included from krdp **6.8.1**. On older versions, type exactly the bare username.

### 3.3 One-day certificate

The 6.7.5 settings page runs `openssl req … -days 1 -batch` **every time it opens** while `AutogenerateCertificates=true` (the default), overwriting any certificate. 6.8 only generates one if none is configured, but it is still 1 day. Windows shows "The remote computer could not be authenticated due to problems with its security certificate" each time it changes. Fix: section 1.3.

### 3.4 Wrong or empty password from Windows

**Symptom:** a `pam_unix(login:auth): authentication failure … user=hs` line followed by `pam_authenticate failure`.

This was the most common failure after the server was fixed. In every case the cause was mstsc sending a stale saved password or an empty one. A debug build logged `password empty: true`. Fix: delete saved credentials in mstsc, tick "Allow me to save credentials", and type the Linux password fresh. Watch for a different keyboard layout on the Windows side (UK vs US changes `@`, `"`, `#`).

### 3.5 Plasma 6.8.0 black screen (stream stalls)

**Symptom:** login succeeds and the window opens, but it stays black. The server log shows the stream starting:

```
Hardware encoding is not supported on this device.
[libx264 @ …] profile Constrained Baseline, level 6.1, 4:2:0, 8-bit
eglChooseConfig returned this many configs: 1
```

and then nothing more.

**Evidence that it is a stall, not a capture problem:**

- The server's CPU use stayed at 0 while connected (section 6.3).
- When the session ended, x264 printed `frame I:1 size:~230000` and `frame P:5`. That's one real keyframe of desktop content and five small frames, then nothing.
- PipeWire showed both nodes `running` (`pw-dump`). KWin was producing NVIDIA tiled DMA-BUF frames (modifier `0x03…`), which turned out not to be the cause.

**Root cause:** krdp 6.8.0 rewrote its video flow control. It now has a dynamic in-flight frame window and pauses the encoder when frames back up ("Encoder backpressure activated"). A client can set `queueDepth = SUSPEND_FRAME_ACKNOWLEDGEMENT` in the RDPGFX frame-acknowledge PDU. 6.8.0 kept those frames pending forever, so the window filled and the encoder paused permanently.

**Fix:** KRDP commit `fe00373` (master) / `472584e` (Plasma/6.8), "VideoStream: Stop waiting for acknowledgements the client suspended", KDE bug **520260**. Included in krdp **6.8.1**. With 6.8.1 the debug log shows backpressure activating and then releasing ("Encoder backpressure released 0"), and frames keep flowing.

### 3.6 Mac client: connection works, but every login attempt fails (2026-10-17)

**Symptom:** the Mac client reaches KRDP, the server log shows

```
New client connected:  Unspecified platform Unspecified version
pam_unix(login:auth): authentication failure; logname=hs uid=1000 euid=1000 tty= ruser= rhost=  user=hs
pam_faillock(login:auth): Consecutive login failures for user hs account temporarily locked
```

then `PostConnect … failed`. The Mac client pops up a generic "We couldn't connect" or "An authentication error has occurred" message.

**Diagnosis:** the krdp server side is fine. FreeRDP is calling PAM with the correct username `hs`, the TLS channel is up, the platform is reported as "Unspecified" (Mac MRD doesn't send a client platform string, unlike `mstsc` which says "Windows NT"). The failure is at the password check, every time.

This is **not** a protocol mismatch and not one of the bugs above. It is the Mac client sending the wrong password — almost always because it cached a stale one.

**Why this happens on Mac but not on Windows:**

- Windows `mstsc` saves the password in Windows Credential Manager, scoped to the target hostname. Delete from "Windows Credentials" → it's gone.
- **Microsoft Remote Desktop for Mac** (the App Store app) does *not* surface a "saved credentials" UI. Passwords are written silently into the macOS Keychain under the connection's name. There is no clear "delete this credential" button anywhere in the app — the only way to force a fresh password is to either:
  1. Edit the connection → **User Account** tab → switch from "Add user account" to **"Ask me every time"**, save, reconnect.
  2. Open **Keychain Access** (`/Applications/Utilities/Keychain Access.app`), search for the box's IP or hostname, and delete the entries with kind "application password".

Other contributing factors seen on Mac:

- **Keyboard layout drift.** If the password was typed on the Mac with a layout that differs from the one the Linux box expects (UK vs US changes `@`, `"`, `#`, `\`), the cached password is wrong even when "typed correctly" on the Mac side. The server still receives *something*, just not the bytes that match `/etc/shadow`.
- **The username box pre-fills a domain.** Older Mac MRD builds sometimes auto-fill `.\hs` or `MACNAME\hs`; with krdp 6.8.1 the `DOMAIN\user` strip fixes that, but if the user account dialog stored the *full* form including the domain in the saved entry, the strip and the saved password may not agree. Use the bare username `hs`.
- **Account lockout after a few wrong attempts.** CachyOS's `pam_faillock` (see §5.1) locks the account after 3 failures in 15 minutes and holds the lock for ~10 minutes. While the lock is active, **the correct password is also rejected** with the same message. This makes the problem look worse than it is: every retry during the lock window just adds to the failed count.

**Fix (do all four steps in order):**

1. **Verify the password first with SSH.** This is the fastest disambiguation. From the Mac, in Terminal.app, run:
   ```bash
   ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no hs@192.168.0.101
   ```
   - If it logs you in → the password is right; the Mac MRD problem is purely a Keychain/cache issue. Continue to step 2.
   - If it says `Permission denied (password)` → the password is wrong. **Stop and fix that first** — change it from a local terminal on the box (`passwd`) and remember the new one. RDP will not work until the password is right. Skip to step 4 if you also need to confirm a fresh password works.

2. **Clear the cached password on the Mac.** Easiest: in MRD, right-click the connection → **Edit** → **User Account** → select **"Ask me every time"** → save. (If "Ask me every time" is greyed out, first switch to "Add user account" with a dummy, save, then re-edit and switch back.)
3. **Reset the CachyOS-side lockout** so you're not fighting `pam_faillock`. From the Mac, over SSH, run:
   ```bash
   ssh hs@<cachyos-host>
   sudo faillock --user hs --reset
   ```
   If you can't SSH either (also locked out), log in physically at the box, or wait 10–15 minutes for the lock window to clear.
4. **Reconnect from MRD.** It will now prompt for username and password. Type the **Linux** password (not your Mac user password, not a Microsoft/Windows password). Make sure the keyboard layout on the Mac is what the CachyOS box expects — try a US layout if your normal one is UK, or vice versa, until the password works. Tick "Remember this password in your keychain" only after you've confirmed it works.
5. **Verify on the server:**
   ```bash
   journalctl --user -u app-org.kde.krdpserver.service -f
   ```
   A successful Mac login looks like:
   ```
   New client connected:  Unspecified platform Unspecified version
   pam_unix(login:account): setuid failed: Operation not permitted     # harmless
   VAAPI: … does not support H264 encoding on this device                # harmless
   Hardware encoding is not supported on this device.                    # harmless, falls back to x264
   ```
   You should **not** see `pam_unix(login:auth): authentication failure`.

**If step 1 said the password is correct but step 4 still fails** (server keeps printing `authentication failure; user=hs`):

The Mac MRD build is sending a password that differs from what the Linux box has, even when you typed "the same thing". Suspect one of these, in order:

- **Keyboard layout drift on the Mac.** The Mac's "Input Source" in System Settings → Keyboard may be different from what you used when you set the password. UK vs US swaps `@`, `"`, `#`, `\`. The password *typed* on the Mac and the password *typed* on the box at creation time are not the same string.
- **A non-ASCII character in the password** (see §5.2). KRDP reads the RDP password with `QString::fromLatin1`, so anything outside Latin-1 (`€`, `£`, em-dash, etc.) is mangled into a different byte sequence and PAM rejects it. Use `passwd` on the box to set a new ASCII-only password and try again.
- **Stale saved credential despite clearing the UI.** Some MRD builds keep the cached password in a *separate* Keychain item (e.g. an "internet password" entry rather than a "generic password" entry). Open **Keychain Access** → search for the box's IP → delete *all* matches. Quit MRD. Reopen.

**Definitive test** for "is MRD sending the wrong bytes, or is PAM getting good bytes but the hash differs?":

```bash
# On the CachyOS box, run this in a terminal as root (or via sudo).
# It traces FreeRDP's auth exchange. Trigger a Mac MRD attempt within 30 s.
WLOG_FILTER='com.winpr.sspi*=TRACE:com.freerdp.core.auth=TRACE:com.freerdp.core.ntlm=TRACE' \
    journalctl --user -u app-org.kde.krdpserver.service -f
```

Look for the line that prints the username and password length received from the client. If the length matches what you typed, the bytes reached KRDP intact and the problem is upstream of PAM (e.g. local vs. cached password mismatch). If the length differs, MRD is mangling the bytes (probably a non-ASCII character or a known MRD/FreeRDP quirk).

**Mac client checklist** (do once per Mac):

- [ ] MRD entry points to the CachyOS box by IP, not hostname (avoids mDNS surprises on locked-down networks)
- [ ] **User Account** set to **"Ask me every time"** (or use a fresh keychain entry — see below)
- [ ] **Display** tab: resolution is a sane single value, not "Multiple displays" (KRDP exposes one virtual monitor)
- [ ] **Sound**, **Folders**, **Clipboard** all **off** unless you want them (clipboard sharing on Mac has caused stalls in earlier KRDP builds)
- [ ] **Gateway** tab: blank. If you set a gateway, MRD will tunnel through it and the server will see the gateway's IP, breaking IP-based allow-lists
- [ ] First connection: at the certificate warning, tick "Don't ask me again" and accept

**Alternative Mac clients** (if MRD keeps misbehaving):

- **Jump Desktop** (App Store) supports KRDP and shows a clear "Forget password" / "Always prompt" toggle. Recommended as a fallback.
- **Royal TSX** is more complex but has explicit credential profiles and a delete button.
- **Microsoft Remote Desktop (the "new" preview)** has the same caching behaviour as the App Store one; switching doesn't help.

### 3.7 Not problems, but expected log noise

These appear on successful connections and can be ignored:

- `[rdp_read_info_packet] Received invalid TPKT header length …`
- `Unexpected client message in state CONNECTION_STATE_FINALIZATION_FONT_LIST`
- `BIO_read returned a system error 104: Connection reset by peer` (mstsc probing or closing)
- `pam_unix(login:account): setuid failed: Operation not permitted` (the account check runs as a normal user; auth still succeeds)
- `QFile::remove: Empty or null file name` (6.8: no SAM file in PAM mode)
- `VAAPI: … does not support H264 encoding` / `Hardware encoding is not supported` on NVIDIA. It falls back to software x264, which works but uses CPU.

## 4. Building krdp locally

### 4.1 krdp 6.8.1 (for Plasma 6.8.0 until the repo has ≥ 6.8.1)

Install build tools explicitly. With `--asdeps`, an orphan cleanup will remove them:

```bash
sudo pacman -S --needed base-devel git cmake extra-cmake-modules plasma-wayland-protocols
```

`scripts/rdp/krdp-build/PKGBUILD` (current):

```bash
pkgname=krdp
pkgver=6.8.1
pkgrel=1
_commit=5813706fff108a40435be2a1c7f3c69f9665d0d0   # Plasma/6.8 "Update version for new release 6.8.1"
...
source=("git+https://invent.kde.org/plasma/krdp.git#commit=$_commit")
build() {
  cmake -B build -S $pkgname -DBUILD_TESTING=OFF -DCMAKE_BUILD_TYPE=Release
  cmake --build build
}
package() { DESTDIR="$pkgdir" cmake --install build; }
```

Build and install. Run the install in a **normal terminal**, because `sudo` prompts didn't work through Claude Code's `!` prefix:

```bash
cd scripts/rdp/krdp-build
rm -rf src pkg; rm -f *.pkg.tar.zst
makepkg -f
sudo pacman -U krdp-6.8.1-1-x86_64.pkg.tar.zst
systemctl --user restart app-org.kde.krdpserver.service
pacman -Q krdp                    # must show the new version
```

To find a newer release commit:

```bash
git ls-remote https://invent.kde.org/plasma/krdp.git 'refs/heads/Plasma/*' 'refs/tags/v6.8*'
```

### 4.2 krdp 6.7.5 (only if stuck on Plasma 6.7.5)

Use the 6.7.5 recipe: tag `v6.7.5` plus two patches. These files aren't the current PKGBUILD:

- `freerdp-3.32-extsecurity.patch`: upstream `573e40a`
- `strip-domain-username.patch`: `DOMAIN\user` fix, plus logging the username and whether the password was empty when a login fails

In `prepare()`: `cd krdp && git apply ../freerdp-3.32-extsecurity.patch && git apply ../strip-domain-username.patch`. Use `pkgver=6.7.5`, `pkgrel=3`, source `git+https://invent.kde.org/plasma/krdp.git#tag=v6.7.5`.

### 4.3 Build gotchas

- **Always use `-DCMAKE_BUILD_TYPE=Release`.** Without it Qt asserts stay enabled, and `Q_ASSERT` in `AbstractSession::setVirtualMonitor` aborts the server as soon as a client connects. The official package has no `qt_assert` symbol: `nm -D /usr/lib/libKRdp.so.* | grep -c qt_assert` returns 0.
- **You can't test a build from its build directory.** KWin only gives the `zkde_screencast` Wayland protocol to `/usr/bin/krdpserver` (whitelisted via its .desktop file). A binary run from `pkg/` segfaults in `PlasmaScreencastV1Session` when a client connects. Install it, then test.
- **Restart after installing.** `pacman -U` doesn't restart the user service; the old binary keeps running until `systemctl --user restart app-org.kde.krdpserver.service`.
- **Don't run `pgrep -f`/`pkill -f` with a pattern that matches your own shell command** when testing in scripts; it kills the shell. Kill by the PID saved from `$!`.
- **Backgrounding `krdpserver … &` from a non-interactive shell can kill it**; use `setsid … < /dev/null &`.

### 4.4 Version numbering so the repo takes over

pacman compares versions with `vercmp`:

```bash
vercmp 6.7.5-3 6.7.5-1.1    # 1  : local patched build beats the broken repo build
vercmp 6.8.0-1.1 6.7.5-3    # 1  : Plasma 6.8 upgrade replaces it automatically
vercmp 6.8.1-1.1 6.8.1-1    # 1  : CachyOS 6.8.1 will replace the local 6.8.1-1
```

CachyOS uses `-N.1` pkgrels, so a local build with `pkgrel=1` of the **same** upstream version is replaced when CachyOS packages it. To override a broken repo build of the same version, use a higher pkgrel (`-2`, `-3`).

## 5. Other things to know

### 5.1 faillock

CachyOS locks an account after 3 failed logins in 15 minutes (`pam_faillock`). The lock also blocks logging in at the machine itself for about 10 minutes. RDP logins count as failures. To check or reset:

```bash
faillock --user hs
faillock --user hs --reset
```

After a reboot `/run/faillock` may not exist until the first root login, so `faillock` as a normal user prints "Permission denied". That's harmless.

### 5.2 Non-ASCII passwords

KRDP (6.7.5 to 6.8.1) reads the RDP password with `QString::fromLatin1` and passes `toLatin1()` to PAM. Characters outside Latin-1 (e.g. `€`) won't match. Keep the password ASCII.

### 5.3 PAM service

KRDP authenticates via the `login` PAM service (`/etc/pam.d/login` → `system-local-login`). The password check uses the setuid `unix_chkpwd` helper, which is fine for the user's own account.

### 5.4 GPU and encoding

On the NVIDIA RTX 3090 Ti, VA-API H.264 encoding isn't available, so KRDP uses software x264. It works, at roughly 30+ Mbit/s on LAN with noticeable CPU use. `KRDP_DISABLE_H264` and `KPIPEWIRE_FORCE_ENCODER` are the only related environment switches in 6.8.

### 5.5 Wayland portal

The log line `Failed to register with host portal … Connection already associated with an application ID` at startup is harmless.

### 5.6 "Other Users" entries

The users loop in `onPostConnect()` returns `false` immediately for any configured user with an empty password, so a leftover test user can block password-based fallbacks. Remove unused entries in System Settings → Remote Desktop. The config key is `Users=` in `~/.config/krdpserverrc`, and passwords are stored in KWallet.

## 6. Diagnostics toolkit

### 6.1 Live log

```bash
journalctl --user -u app-org.kde.krdpserver.service -f
```

### 6.2 Debug logging (temporary)

```bash
D=~/.config/systemd/user/app-org.kde.krdpserver.service.d
mkdir -p "$D" && cat > "$D/debug.conf" <<'EOF'
[Service]
Environment="QT_LOGGING_RULES=org.kde.krdp.debug=true;kpipewire_logging.debug=true;kpipewire_dmabuf_logging.debug=true;kpipewire_record_logging.debug=true;kpipewire_libav_logging.debug=true"
EOF
systemctl --user daemon-reload && systemctl --user restart app-org.kde.krdpserver.service
# … reproduce … then remove:
rm -r "$D" && systemctl --user daemon-reload
```

Useful debug lines: `PAM authentication succeeded for user`, `Encoder backpressure activated N` / `released N`.

FreeRDP's own tracing goes through the `WLOG_FILTER` environment variable, e.g. `WLOG_FILTER='com.winpr.sspi*:TRACE,com.freerdp.core.auth:TRACE'`.

### 6.3 Is video flowing?

```bash
P=$(systemctl --user show -p MainPID --value app-org.kde.krdpserver.service)
a=$(awk '{print $14+$15}' /proc/$P/stat); sleep 3; b=$(awk '{print $14+$15}' /proc/$P/stat)
echo "cpu ticks in 3s: $((b-a))"     # 0 while connected = stalled stream
```

Per thread: `for t in /proc/$P/task/*; do echo "$(cat $t/comm) $(awk '{print $14+$15}' $t/stat)"; done`. Watch `PipeWireProduce` and `krdp_session`.

When a session ends, x264 prints `frame I:` / `frame P:` counts. A handful of P-frames for a long session means it stalled.

### 6.4 Is anyone connected?

```bash
ss -tn state established '( sport = :3389 )'
```

### 6.5 PipeWire stream state

```bash
pw-dump | python3 -c '
```
